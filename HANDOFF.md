## 1. Суть проекта (коротко)

**Flight Ticket Advisor** — web-приложение (платформа), которое для конкретного направления и диапазона дат отвечает на вопрос:

> **Когда (от текущей даты до даты вылета) будет минимальная / наиболее выгодная цена покупки билета.**

**Ядро продукта — ML-прогноз цены (CatBoost), а НЕ LLM-чат.** AI-чат — лишь один из двух способов ввода (форма + чат) и идёт в последнюю очередь (фаза 6).

**Целевой кейс пользователя:** октябрь 2026, человек смотрит Москва→Токио на март 2027 (вылет 20–26 марта, прилёт 4–7 апреля) на Trip.com/Aviasales. Вчера цена 100 000 ₽, сегодня 102 000 ₽. Платформа должна сказать «когда покупать», на основе исторических данных + контекста (новости/риски, календарь).

**Стек (согласовано):** Python 3.13 + FastAPI + SQLite (MVP) + APScheduler (позже) + CatBoost (позже) + Streamlit (UI). Без LangGraph/CrewAI — «агенты» это просто Python-модули с интерфейсом `run(query) -> result`.

## 3. Архитектура

```
Streamlit UI (форма + dashboard [+ чат])  →  FastAPI
  /api/recommend  /api/calendar  (+ позже /api/track /api/news /api/alerts)
        │
   ┌────┴────── 4 движка + оркестратор ────────────────────────────┐
   │ price_engine    CORE: цены → CatBoost → траектория + дата покупки│
   │ alerts_engine   поллинг цен → дельта vs медиана → «упала/растёт» │
   │ news_engine     GDELT+RSS → risk-скор (без LLM)                 │
   │ calendar_engine VK Workspace → busyness → свободные окна         │
   │ orchestrator    weighted score → BUY_ON_DATE / WAIT / AVOID      │
   └───────────────────────────────────────────────────────────────┘
   SQLite (MVP) → Postgres + Redis; APScheduler — поллеры
```

### Этап 3 — ✅ выполнен (alerts_engine + orchestrator: вердикт BUY/WAIT/WATCH, 2026-10-25)
- **`backend/app/engines/alerts_engine.py`** — `dynamics(origin, dest, dep_date, return_date=None)`:
  сравнение последней цены с **медианой** предыдущих измерений (устойчивее среднего к выбросам).
  История — снапшоты поллера (цикл 4 ч). `< 2` измерений → `status="collecting"` (честно сообщаем).
  Δ в пределах ±2% (`STABLE_THRESHOLD_PCT`) → «стабильно», иначе «растёт»/«падает».
  Возврат: `{status, latest, median, delta_pct, direction, measurements, text}`.
- **`backend/app/engines/orchestrator.py`** — `verdict(res, news, dyn) -> dict` — **итоговый вердикт «когда покупать»** из 3 сигналов:
  1. 📅 Календарь цен: минимум ≥3% (`CHEAP_DISCOUNT_PCT`) ниже средней → impact `buy`, иначе `neutral`;
  2. 📈 Динамика: растёт→`buy`, падает→`wait`, стабильно/collecting→`neutral`;
  3. 📰 Новости: `risk_level="warning"` → `careful` (+⚠️ в текст вердикта), иначе `neutral`.
  Скор: buy=+1, wait=−1, neutral=0 → `BUY` / `WAIT` / `WATCH`; нет цен → `no_data`.
  `confidence`: medium если динамика ok, иначе low. **Принцип «объяснимый AI»**: каждый вердикт сопровождается списком сигналов с объяснениями (демо-материал для защиты).
- **UI** (`frontend/app.py`): карточка вердикта (`.verdict-BUY/-WAIT/-WATCH/-no_data`, цвет по сигналу) над карточкой рейса; список «Сигналы вердикта» (`.signal-item.impact-buy/wait/careful`); в секции «Динамика цены» подпись dynamics() для выбранной даты.
- **Контекст AI-чата**: `chat_engine.build_context` теперь включает `verdict` (signal/title/text/signals) и `price_dynamics` (direction/delta_pct/measurements) — помощник объясняет вердикт.
- **Верификация**: py_compile ✓; юнит-тест 7 сценариев оркестратора (BUY/WAIT/WATCH/careful/collecting/no_data/одна дата) ✓; живая dynamics() на истории поллера (MOW→TYO 20.03 one-way: 4 измерения, стабильно 0.0%; round-trip: collecting) ✓; AppTest round-trip сабмит: 0 исключений, вердикт BUY, 3 сигнала, GF-кнопка ✓.
- Поллер жив (pid из `data/poller.pid`, работает с 2026-10-24 ~23:38).

Стабильно на всех датах/валютах; при этом MOW→LED цены даёт → это не «domestic»-эффект, а особенность конкретного перевозчика. Фикс:

Кэш в SQLite: новая таблица `fx_rates` (pair PK, rate, fetched_at), TTL `FX_TTL_HOURS = 12` (config.py), функции `db.latest_fx_rate/save_fx_rate`.
- **Конвейер конвертации** (`price_engine.get_price_calendar`): исходный цикл вынесен в `_fetch_calendar(..., currency, ...)`; при 0 цен и currency != USD → `fx.get_rate("USD", currency)` → повторный проход в USD → `price` и `cheapest_offer.price` умножаются на курс (`int(round(...))`), записи помечаются `"fx": {"from": "USD", "rate": …}` и пересохраняются снапшотами **в целевой валюте** (следующие запросы берут из кэша). `recommend()` отдаёт `res["fx"]`. UI (app.py): caption «💱 Google Flights не отдал цены в {currency} — найдены в USD и сконвертированы по курсу ЦБ РФ: 1 USD = … {currency}». Точность: 266 USD → 21 411 ₽ против реальной RUB-цены 21 399 ₽ (Δ≈0.06%).
- **Гоча кэша**: `db.latest_snapshot` получил параметр `currency: str = "RUB"` c `AND currency IS ?` — раньше USD-снапшот мог отдаться RUB-запросу внутри 24ч TTL.
- **Виза-предупреждение (🔴/⚠️)**: `check_trip(country, dep_start, ret or dep_end_eff)` вызывается в submit-handler, результат в `res["_visa"]`. Рендер до блока «занят»: `overstay=True` → `st.error("🔴 … дата вылета обратно превышает допустимый лимит нахождения в стране для граждан РФ")`, иначе `st.warning("⚠️ … проверьте, нужна ли виза для граждан РФ… перепроверьте на МИД/консульство")`. `visa_engine`: ветка visa_free без лимита дней теперь возвращает инфо-дикт (а не None) → «срок пребывания не ограничен»; 🛂 убрана из headline (иконку ставит UI). Страна/Россия/нет в справочнике → предупреждения нет. trip_days = (ret − dep + 1), окно = возвращение, иначе конец диапазона, иначе сама дата.
- **«Дата вылета (по)» ≥ «Дата вылета»**: оба date_input вынесены ИЗ `st.form` (внутри формы виджеты не триггерят rerun — min_value обновился бы только после сабмита). Теперь `min_value=dep_start or _today` у dep_end. Устаревшие значения ловит валидация на сабмите («Дата «по» должна быть не раньше даты вылета»). ## 5. Ключевые технические детали (важно для продолжения)

### 5.1. Скрейпер Google Flights (рабочая логика)
- **fast_flights 3.1.0 как библиотеку использовать НЕЛЬЗЯ** (её HTTP-клиент `primp` не резолвит DNS/таймаутит в этой среде; парсер местами падает). НО `fast_flights.create_query` + `FlightQuery` **работают для построения URL** (protobuf-параметры `tfs`).
- Страницу качаем через `httpx`, при ошибке — **`curl` subprocess (в этой среде curl надёжнее всего)**.
- Парсим встроенный JSON: `AF_initDataCallback` в теге `script.ds:1` → `payload[3][0]` = список офферов.
- Структура оффера: `k[1][0][1]` = **цена**; `k[0]` = детали рейса; `k[0][1]` = авиакомпании; `k[0][2]` = сегменты (в сегменте `sf[3]`=from, `sf[6]`=to, `sf[20]`/`sf[21]`=даты вылета/прилёта).
- Уже написанный и рабочий код: `backend/app/tools/gf.py` (функции `search_flights`, `parse_flights`, `_fetch_html`, `_parse_payload`).

### 5.2. Особенности сети (важный блокер)
- **httpx** — периодический `ConnectTimeout: _ssl.c:1011: The handshake operation timed out` (флаки).
- **primp** — `DNSTimeoutError`, не работает вообще.
- **curl** — работает стабильно.
- Python `urllib`/SSL — нужен `certifi` (уже установлен); при `CERTIFICATE_VERIFY_FAILED` ставить `SSL_CERT_FILE=certifi.where()`.
- **Установка pip-пакетов идёт крайне медленно / зависает** (сеть нестабильна). `fastapi uvicorn streamlit pandas` в итоге установились (проверено: импортируются), но процесс pip-установки завершался с ошибкой выхода — при будущих доустановках быть готовым к повторам/долгим таймаутам.
- **Замер 2026-10-27 (Linux, RU-IP, `bench/run_scraper_bench.py`)**: httpx p50 0.86 с, curl p50 9.6 с, оба 0 ошибок на 10 маршрутах → порядок «httpx, затем curl» верный; на Mac автора httpx был флаки, поэтому fallback оставлен.
- **Облако (Streamlit Cloud, США/ЕС)**: без cookies `CONSENT`/`SOCS` Google отдаёт страницу согласия; при блокировке IP — капчу (нужен `GF_PROXY`).

### 5.3. Холодный старт (ключевой продуктовый нюанс)
Собственной истории цен ещё нет (копится месяцами). Поэтому в Этап 1 **CatBoost-прогноз НЕ делаем** — вместо него:
- календарь «цена × дата вылета» (min-цена на каждую дату диапазона);
- эвристика «покупай заранее» (цены обычно растут ближе к вылету);
- накопление снапшотов в SQLite (основа будущей истории).

Это честно помечается в UI. Полный прогноз «когда покупать» = Этап 2+ (после накопления истории или через `price_insights` Google Flights / Travelpayouts).
